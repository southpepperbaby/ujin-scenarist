# Концепт продукта (рабочее название: Сценарист)

Хакатон Ujin / ЭР-Телеком, 31 октября - 1 ноября 2026. Команда ERRD TEAM: Ваня, Артём, Тимур, Варя, Саша.
Этот файл - источник правды для кода и презентации. Решения, которые привели к нему, в `decisions.md`.

## Задача организаторов

Разработать редактор пользовательских сценариев для умных устройств на базе Ujin OS: описывать устройства и их
возможности на одном языке, настраивать правила взаимодействия, проверять сценарии на эмуляторах оборудования.

Шесть подзадач, по которым жюри ставит галочки:
1. Конструктор устройств.
2. Эмуляторы устройств.
3. Редактор пользовательских сценариев.
4. Исполнение сценариев.
5. Интеграция с платформой Ujin OS.
6. Пользовательский интерфейс и демонстрационные сценарии.

Критерии: технологичность (работоспособность и качество кода, фреймворки, количество и сложность технологий),
соответствие шести подзадачам, потенциал (реализуемость за год, ценность, roadmap, конкурентные преимущества).

## Что строим

Веб-приложение, одна кодовая база, две роли: житель и управляющая компания (УК).
Редактор сценариев умного дома, где правила создаются разговором с ИИ, проверяются до включения
(линтер и прогон на эмуляторах) и исполняются нашим движком на эмуляторах и на платформе Ujin.

Формула: **LLM пишет, Jev судит, эмулятор проверяет, движок исполняет.**

## Пользователи

- **Житель.** Телефонный экран: чат «опиши правило словами», мои правила, мои устройства, мои заявки.
  Правит правила своей квартиры.
- **УК (диспетчер).** Большой экран: квартиры и общедомовое оборудование, лента инцидентов, очередь заявок,
  пул подрядчиков, правила уровня дома. Правила УК приоритетнее правил жителя при конфликте.

## Единый язык описания устройств

Берём формат декларации из пакета Ujin (`declaration()` эмуляторов): у устройства есть сигналы, каждый сигнал имеет
`name`, `title`, `control` (тип значения), `management` (r / rw / w), `kind` и группу:
- **свойства** (property): что устройство измеряет, только чтение;
- **возможности** (capability): чем можно управлять, rw / w;
- **настройки** (setting): пороги, таймеры, периоды.

Конструктор устройств создаёт новое устройство из этой же декларации (клон существующего семейства плюс правка
сигналов) и регистрирует его как эмулятор. Экспорт устройства идёт в формат Ujin без преобразований.

## Правила

Правило = `когда` (событие сигнала) + `если` (условия по другим сигналам, времени, роли) + `то` (список действий).
Действия: выставить сигнал устройства, уведомить (житель / УК / канал), создать заявку подрядчику, запустить
другое правило. Хранятся как JSON по строгой схеме, редактируются и в чате, и блоками руками.

Статусы правила: черновик → проверено линтером → прогнано на эмуляторе → включено.
Экспорт в формат Ujin autoscripts (`when:device-<sn>:<signal>=<v>` / `device-<sn>:<signal>:<v>[:hold]`)
для совместимости с платформой.

## Киллер-фичи

1. **Прогон до включения.** Правило гоняется на эмуляторах с ускоренным временем, лента событий показывает,
   что сработало и почему. Ни один потребительский редактор этого не даёт (см. `competitors.md`).
2. **Линтер правил.** Конфликты за одно устройство, циклы (А запускает Б, Б запускает А), недостижимые условия,
   обращение к несуществующему сигналу. Проверка до сохранения.
3. **Естественный язык с верификацией.** Пользователь пишет текст, LLM возвращает JSON-правило по схеме,
   система показывает карточку «вот что я понял», затем линтер и прогон. Обратно: любое правило объясняется
   простым языком. Jev до генерации отличает разовую команду от постоянного правила.
4. **Автодиспетчер (главная фича).** Инцидент с устройства классифицируется Jev (категория, серьёзность, риск
   ущерба, ложная тревога, дубликат), политика по уровням решает, что делать, заявка уходит нужному подрядчику
   из пула УК без цепочки «житель → управляющий → подрядчик».
5. **Две роли и два уровня правил.** Квартира и дом в одном продукте, приоритет УК при конфликте.
6. **Интеграция с Ujin.** Сигналы эмуляторов публикуются на стенд, события видны в кабинете УК (BMS) и у жителя.

## Автодиспетчер: политика и quality gates

Конвейер: сигнал → инцидент → Jev → политика → действие → журнал.

Уровни:
- **0, информация** (садится батарейка): только журнал.
- **1, минор** (свет не включается, риска нет): заявка-черновик, житель подтверждает одной кнопкой.
- **2, мажор** (ворота заклинило, лифт встал пустой): заявка создаётся сама, УК может отменить в течение 10 минут.
- **3, критично** (протечка, дым, лифт с людьми): сначала правило-смягчение (перекрыть воду), затем заявка и
  звонок диспетчеру без ожидания.

Gates: порог уверенности Jev (выше 0,85 автономно, 0,6-0,85 спросить человека, ниже только журнал), самотест
устройства перед вызовом, защита от дребезга (тревога держится N секунд), дедупликация (одно устройство, одна
открытая заявка), лимит заявок на устройство в сутки, рабочие часы и SLA подрядчика, лимит стоимости, журнал
каждого автономного действия с объяснением простым языком.

Пул подрядчиков в MVP: таблица в панели УК (компания, категория, контакт, SLA).
Заявка в MVP: запись у нас плюс сообщение в Telegram-чат «подрядчика».

## Модели

- **LLM через OpenRouter** (модель в конфиге, старт с Qwen3): генерация правила из текста, объяснение правила,
  текст заявки. Открытая модель, в проде разворачивается у УК on-prem.
- **Jev (TypeSafe) через OpenRouter:** типизированные вердикты с вероятностями для маршрутизации, серьёзности,
  риска, дубликатов, ложных тревог, «разовая команда или правило». Вероятность = quality gate.
- **Конфиденциальность:** наружу уходит только текст правила и обезличенный список устройств. Идентификаторы
  подменяются псевдонимами, обратная таблица живёт у нас. Ответ модели валидируется по схеме.
- **Roadmap:** API-модель генерирует датасет «текст → правило», на нём дообучается локальная модель 7-8B.

## Стек

- Бэкенд: Python 3.12+, FastAPI, Pydantic, WebSocket, SQLite (SQLModel), эмуляторы из пакета Ujin как база.
- Фронтенд: React, TypeScript, Vite, Tailwind, React Flow для блочного редактора, Zustand.
- Инфра: Docker Compose, один `docker compose up`.
- Интеграции: Ujin API (стенд uae-test), OpenRouter (LLM + Jev), Telegram Bot API для заявок.

## Демо-история (5 минут, скринкаст)

Протечка на кухне ночью. Житель заранее написал правило словами. Датчик намок → вода перекрыта (реле счётчика)
→ свет в коридоре включился → житель получил пуш → УК увидела инцидент в ленте → Jev оценил как критичный →
заявка ушла сантехникам в Telegram → шлагбаум открылся для аварийной бригады. Пять устройств стенда задействованы.

## Roadmap на слайд

Сценарии уровня нескольких домов и ЖК, маркетплейс шаблонов сценариев, версионирование и откат правил,
прогон правил на истории реальных сигналов, локальная модель on-prem, интеграция с биллингом подрядчиков.
